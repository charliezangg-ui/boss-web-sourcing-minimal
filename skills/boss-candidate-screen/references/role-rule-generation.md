# 新岗位规则生成与确认

发现尚无有效规则 JSON 的岗位时，自动读取同岗完整 JD、用户已确认的公司通用规则与岗位补充，生成 `role-rules.json`。使用[完整结构模板](role-rules.template.json)，保存到本运行的私有可写目录，并在运行账本记录路径、版本和来源。结构完整不代表取值齐全；未知字段保留 null 与缺口，不能编造值。

## 生成顺序

1. 核验岗位身份、城市、JD全文及版本；同名岗位也核验实际身份。公司通用规则与岗位规则分层引用，逐条保存来源。
2. 提取正式工作年限、候选人期望薪酬、技术栈、项目交付、本人责任及证据要求；区分必要项、加分项和明确例外。保留原要求的 AND/OR，不将“至少一种”改为“全部”。
3. 对尚未确认且已列明的可比较选项，默认选择最严格方案，保存备选、采用项、理由及出处。此默认仅处理剩余选项；已确认的宽松方案、例外与数值继续有效。无明确选项或无法比较严格程度时记录缺口，不创造数值、白名单或额外条件；加分项保持加分项。
4. 新岗位的薪资、年限必须由用户确认，集中一次提问。本次指令已明确两项即记录为 confirmed；仅 JD、历史其他岗位或 Agent 建议不能代替确认。“默认最严格”也不能代替这两项确认。同一运行续跑复用确认。
5. JSON 与来源、例外、候选条件逐项核对。薪资或年限待确认时标记 `awaiting_confirmation`；其他决定性字段缺失或冲突标记 `configuration_incomplete`。只有确认齐全、缺口清空，才标记 `ready` 并交给筛选器与评审模块。

## 执行边界

自动生成规则不是自动开始招聘的授权。新岗位启动须处于用户已授权的岗位与动作范围，并满足薪资、年限确认门槛；缺少任何一项则只准备规则，不提交筛选器、不筛人触达。用户明确授权所有在招岗位可覆盖相应岗位，但仍核验上述确认。

评审逐人引用冻结的 JSON 版本；规则变更生成新版本并复核待发送候选人，保留历史发送事实。公司规则未提供时如实记录未提供，不继承本包外的私有标准。年龄、性别、家庭等非工作属性不参与严格选项选择。

## JSON 填写契约

模板中的 null、空数组和 draft 是待填写占位，不是默认通过。`requirements` 每项包含 id、condition、operator（all/any/threshold）、value、evidence_required、source、status；`exceptions` 单列明确例外；`unresolved` 保存缺口。`remaining_option_decisions` 保存 options、selected、source、reason。`ready` 必须满足：岗位/JD已绑定、salary和experience均confirmed、必要条件均有来源、unresolved为空、execution_authorization有用户指令依据。生成后检查 JSON 可解析及这些状态条件，再交接；任何失败即时写入运行记录。
